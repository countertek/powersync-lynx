# Desktop support (0.3.0): first-class native CMake `LynxView` and Lynxtron on `macos/arm64` and `windows/x64`

For `0.3.0`, `powersync-lynx` promotes **both** native CMake `LynxView` and Lynxtron Autolink to first-class supported desktop tiers on **`macos/arm64`** (macOS 14.0+) and **`windows/x64`** (Windows 10+). `macos/x64` is dropped; `windows/arm64` and `windows/x86` are deferred.

## Decisions

1. **Single npm package with prebuilt desktop artifacts**: Ship prebuilt `dist/macos/arm64/` (`powersync-lynx.node` + `libpowersync_aarch64.macos.dylib`, ad-hoc signed) and `dist/windows/x64/` (`powersync-lynx.node` + `powersync_x64.dll`) inside the single `powersync-lynx` tarball via a multi-OS release workflow. Browser web bundles are unaffected (0 bytes impact). Release packaging fails if stray `macos/x64` or `linux/x64` binaries appear in `dist/`.
2. **Native MSVC Windows `.node` build**: Build `dist/windows/x64/powersync-lynx.node` natively on Windows with MSVC + CMake using `@lynx-js/lynx-library-headers`'s `lynx_link_lynxtron_runtime`, retiring `shared/win_host_stubs.c` and the Zig mingw `win-node` cross-compile target to avoid CRT/ABI mismatches.
3. **Standalone CMake target for native `LynxView` apps**: Split `shared/CMakeLists.txt` so native embedders link a clean `powersync_lynx_native` target via `add_subdirectory(...)` (no `native-vendor/` dependency, no `lynxtron/library_entry.cc`), call `LynxEnv::GetInstance().RegisterNativeModule("NativePowerSyncModule", CreateNativePowerSyncModule, nullptr)`, and stage `powersync-sqlite-core` via a CMake helper.
4. **Dynamic macOS `powersync-sqlite-core` lookup**: macOS keeps dynamic `libpowersync_aarch64.macos.dylib` via `dlopen` + `sqlite3_auto_extension` (matching the pinned release asset), probing `POWERSYNC_CORE_PATH`, `<ModuleDirectory>/`, and `<ModuleDirectory>/../Frameworks/` (for native macOS `.app` bundles). This supersedes the earlier `docs/spec.md` table note describing macOS as static auto-extension.
5. **Safe default `dbLocation` and Windows UTF-8 paths**: When `dbLocation` is omitted on desktop (and `dbFilename` is relative, non-`:memory:`, non-`file:` URI), resolve and auto-create an OS app-data directory: `~/Library/Application Support/<app>/` on macOS (`CFBundleIdentifier` in `.app` bundles, else executable name, fallback `powersync-lynx`) and `%LOCALAPPDATA%\<app>\` on Windows (executable stem, fallback `powersync-lynx`). Windows path APIs use UTF-16/UTF-8 wide-char calls (`GetModuleFileNameW`, `_wstat`, `SHGetKnownFolderPath`, `CreateDirectoryW`).
6. **Desktop `/sync/stream` via Native Module HTTP (Gate #73 — Branch B triggered)**: Empirical verification on native CMake `LynxView` 4.2.0 (`LynxHttpService` is buffered-only with no incremental chunk callback or cancel hook) and Lynxtron 0.0.31 (`LynxFetchModule.fetch` hangs on macOS arm64; `AbortSignal` does not close the native socket) triggered the [ADR 0003](0003-native-module-http-is-streaming-fallback.md) contingency. Desktop `NativePowerSyncModule` (`shared/nativeModule/`) now exposes `httpFetch` / `httpFetchAbort` backed by `NSURLSession` on macOS and `WinHTTP` on Windows, sharing `shared/sync_http/sync_http_{engine,session}.{h,cc}` and `shared/sync_http_policy.h`, and delivering `GlobalEventEmitter` events directly via `Napi::Env` + `Napi::ThreadSafeFunction` (zero host wiring required).
7. **Runnable showcase hosts and CI**: Replace recipe-only `examples/hosts/desktop/` with runnable `examples/hosts/macos/`, `examples/hosts/windows/`, and `examples/hosts/lynxtron/` (with a pinned, SHA-256-verified Lynx 4.x Desktop C++ SDK fetcher and `LYNX_SDK_DIR` override), add `macos-14` + `windows-latest` CI jobs (including headless Windows E2E sync verification), and verify live two-client sync across all four OS × host combinations before tagging `0.3.0`.
